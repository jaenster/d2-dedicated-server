# Native-port surface: which engine functions a headless GS actually needs

The d2gs server today is the **stock 1.14d engine** driven by an injected DLL.
To port it to native (drop `Game.exe`) we need to know *which* engine functions a
headless server actually touches — and which giant chunks (rendering, UI, sound)
it never does. Static answer, computed from the reconstructed 1.14d.

Generated by `tools/native-surface` (Zig). Regenerate:

```sh
cd tools/native-surface
zig build run -- --recon "$D2_RECON_SRC" --out ../../docs/architecture/native-surface --edge-min 30
dot -Tpng ../../docs/architecture/native-surface/server.dot -o ../../docs/architecture/native-surface/server.png
```

## Method

Reads the reconstruction's per-file `*.cpp.map` JSON sidecars — each lists every
function with `address`, `namespace`, and Ghidra-resolved `calledFunctions`, so
direct call edges are authoritative. Windows-range addresses only
(`0x400000–0x6fffff`; the maps also carry Mac variants).

**Indirect dispatch is recovered.** D2 runs its skill / missile / AI / object /
qserver systems through function-pointer tables indexed by `.txt` columns at
runtime — `call [table + idx*4]`, which Ghidra can't resolve, so those handlers
appear in *no* `calledFunctions`. They show up instead as `&FunctionName`
address-taken refs in the `.cpp` text. We scan those, and seed the closure on
**the 91 `SCMD_0x*` command handlers ∪ every address-taken function in a server
namespace** (~909 of them), then BFS the callees.

Classification is by namespace (`D2Common::Unit::SUnit` → `D2Common/Unit`).
Client/render/sound (`D2Client/*`, `D2Win`, `D2Sound`, `D2CMP`, `D2OpenGL`) are a
**cut boundary**: counted when reached (a native server stubs that edge) but not
traversed into, so a single server→client edge doesn't unfold the whole client.

## Headline result

Total reconstructed Windows functions: **13,339** (16,107 incl. Mac).

| | reachable | server-relevant | client boundary |
|-|-|-|-|
| server port surface | **4,839** | **4,534** | 305 |

**~4,534 functions** is the real native-server surface — roughly **a third** of
the engine. The other ~8,800 (rendering, UI, sound, input, the client) drop.

### Why this is ~2× an earlier estimate

A direct-`calledFunctions`-only closure gives ~2,477 and looks clean — but it's
**wrong**: it stops at every dispatch table. Those tables hold the actual
gameplay:

| handler class | exist | recovered |
|-|-|-|
| skill srv/clt dofuncs | 360 | ✓ |
| missile functions | 287 | ✓ |
| AI handlers | 339 | ✓ |

Recovering the indirect edges pulls in those ~970 handlers **plus their
transitive callees**, ~doubling the surface. The jump is visible per subsystem:
`D2Game/Monster` 47 → 401, `D2Game/Missiles` 5 → 129, `D2Common/Skills` → 294.

## Holes — what the surface needs but doesn't contain

[`server_holes.md`](server_holes.md) classifies every symbol the ~4.5k server
functions reference but the set doesn't satisfy. Compiling the slice can't be the
oracle (the reconstruction doesn't type-check — ~150 errors/file from incomplete
structs), so this is computed from the `.cpp.map` data instead.

- **External (37)** — referenced, not reconstructed: CRT (`_memcpy`, `_sprintf`,
  `__alldiv`, `_fopen`), Win32 (`GetTickCount`, `InitializeCriticalSection`,
  `WSAGetLastError`), intrinsics. The native "must implement/link" list.
- **Client/render/sound boundary (307)** — server calls into pruned code; each a
  stub point: `SOUND_PlaySound` (no-op), `GFX_*` (no-op), `GetUIFlag`/`SPELLSEL_*`
  (UI state). Watch for mis-filed helpers — e.g. `D2ApplyPercent` (48 calls) is
  math under `D2Client/_SkillHelpers`, a reimplement not a stub.
- **Ambiguous gaps (6)** — reconstructed server fns whose edges were dropped on a
  cross-module name collision (`HasWaypoint`, `Transmorgify`, …); force-include.
- **Type surface (1062)** — structs the set touches: `D2UnitStrc` (2556×),
  `D2GameStrc`, `D2RoomStrc` first. This is the data-dependency surface to define.

## Caveats

- **Static, not dynamic.** Everything *reachable*, not everything *hit at
  runtime*. A runtime boundary trace would give the smaller exercised set.
- **Indirect roots are coarse.** Every address-taken server function is seeded —
  a few may be dead in shipped `.txt` data. Over-inclusion, not under: safe for a
  worklist.
- **Data globals still not modelled** — call edges only. Shared state
  (`sgptDataTable`, the property-function tables) is a separate surface; the maps
  carry `usedTypes` per function to scope it next.
