# Which engines the end-to-end run covers, and what each is expected to manage.
#
# ONE place, so promoting an engine is a one-line change and a regression is a hard failure rather
# than something someone notices three weeks later. This file exists because the failure mode here
# is never "the build breaks" — it is that a fix for one version quietly stops another serving, and
# every one of those looks identical from the client: the join is accepted and nothing arrives.
#
#   world   a real client must reach a NON-EMPTY world. Anything less fails the run.
#   boot    the server must start, publish itself into the store, and keep a clean log. Not yet
#           expected to hand out a world; the reason is in the note.
#   broken  known not to work, for the recorded reason. The run asserts it fails THE SAME WAY — and
#           fails if it starts working, because a record nobody updates is a record nobody trusts.
#
# Never downgrade a row to make a run pass. A `world` engine that stops serving is the exact
# regression this file exists to catch.
#
# The game tree is an INPUT here, not something the build produces, and it is the thing most likely
# to be wrong. tools/make-minimal-engine.sh is the recipe; what actually gets tested is the
# published d2-<engine>-minimal.tgz, and changing the recipe does not change that tarball. A tree
# built to an older recipe fails as an engine assert with nothing pointing at the tree, so when a
# row that used to hold starts failing, check the tarball's age against the recipe's before the code.
