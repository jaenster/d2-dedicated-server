# Which engines the end-to-end run covers, and what each is expected to manage.
#
# ONE place, so promoting an engine is a one-line change and a regression is a hard failure rather
# than something someone notices three weeks later. This file exists because the failure mode here
# is never "the build breaks" — it is that a fix for one version quietly stops another serving, and
# every one of those looks identical from the client: the join is accepted and nothing arrives.
#
# 1.07 is deliberately NOT a row here: it is not a target. It is still REQUIRED, though, and by the
# build rather than by this file — every expansion DLL from 1.08 on is a delta against 1.07's PE
# files (`D2_LOD_BASE` in tools/make-minimal-engine.sh), so the tree recipe cannot lose it. What is
# dropped is serving it, not having it.
#
#   world   a real client must reach a NON-EMPTY world. Anything less fails the run.
#   boot    the server must start, publish itself into the store, and keep a clean log. Not yet
#           expected to hand out a world; the reason is in the note.
#   broken  known not to work, for the recorded reason. The run asserts it fails THE SAME WAY — and
#           fails if it starts working, because a record nobody updates is a record nobody trusts.
#
# Never downgrade a row to make a run pass. A `world` engine that stops serving is the exact
# regression this file exists to catch.
#
# The game tree is an INPUT here, not something the build produces, and it is the thing most likely
# to be wrong. tools/make-minimal-engine.sh is the recipe; what actually gets tested is the
# published d2-<engine>-minimal.tgz, and changing the recipe does not change that tarball. A tree
# built to an older recipe fails as an engine assert with nothing pointing at the tree, so when a
# row that used to hold starts failing, check the tarball's age against the recipe's before the code.

1.08   boot    # driven now: creates a game, handshakes and TAKES THE CHARACTER (its record is
               # 1.07's shape with its own number, 0x59, out of its own writer). Then the same null
               # jump as 1.06b.
1.09b  boot    # driven too, and takes the character. Its record is NOT 1.08's shape: it keeps the
               # modern layout and only the version differs (0x5c), so rewriting the header the
               # 1.08 way would break a save it would otherwise accept. Then the same null jump.
               # Must NOT be given Patch_D2.mpq — the 1.14d-era one faults it during boot
1.09d  boot    # boots from the PUBLISHED tree, which carries 1.09d-era compiled tables. It was
               # recorded as broken off a locally assembled tree whose data/ held the recovered
               # tables instead: loose files win over MPQ members, so the wrong-era ones are what
               # the engine reads, and it asserts "nLoadedValue < MAX_SKILL_RESTRICTED_STATES"
               # (DataTbls.cpp:0x231). The engine was never the problem; the tree was.
1.10f  world   # verified: stock 1.14d client in the Rogue Encampment, 145 packets. Needs Patch_D2
1.13c  world   # verified: same, plus 179 packets / 53 units via the clientless. Needs Patch_D2
1.06b  boot    # classic lineage: d2data only, no d2exp, and its own Fog rewrite. Now creates a
               # game, takes a character and completes the handshake with a client framing it as
               # classic (GameFlags is SIX bytes here). It refuses the character with Error:9,
               # which is the save-version gate: 1.06b requires EXACTLY 0x47 (@0x6fcf7827) and the
               # realm hands every engine 0x60. Same root as 1.07 — see the note there.
               #
               # What it wants is not the modern .d2s at all but a 130-byte record: magic, version,
               # name[16] at 0x08 (strcmp'd against the client's), status at 0x18, a content
               # revision at 0x1c (0xdd here, 0x13f on 1.07), 0x10 at 0x1e and the size 0x82 at
               # 0x20. Writer @0x6fcf6a10, parser @0x6fcf77c0.
               #
               # The parser has SEVEN return-9 paths, not three — a scan stopping at 0x6fcf7c00
               # sees only the first three, and the rest are counter-bumping blocks that conditions
               # further up jump into. Relative to the record: word[0x20]==0x82, dword[0x04]==0x47,
               # strcmp(client, 0x08), word[0x1c]<=0xdd, word[0x1e]<=0x10, word[0x22]<5, and
               # byte[0x58] nibbles <4 and <3. A record satisfying all seven STILL returns 9, so
               # the next move is to dump the record as DELIVERED from d2host rather than infer it
               # from the database row.
               #
               # Of those, two are provably satisfied once
               # that record is delivered: word[rec+0x20]==0x82 (@0x6fcf77f3) and
               # dword[rec+0x04]==0x47 (@0x6fcf7827, and the host logs ver=0x47 going out). What is
               # left is the third: `strcmp(clientName, rec+0x08)` @0x6fcf787a, the record's name
               # against the name the engine holds for the client. The record's half is confirmed
               # good — the host logs "declared=1668572506", which is the name read as a dword at
               # offset 8 — so the disagreement is on the CLIENT side of that compare, which is
               # where d2host translates the 1.14d join. That is the next thing to look at, and it
               # is one comparison rather than a format.
               #
               # RESOLVED. It was the checksum: the modern save keeps one at 0x0C, and 0x0C is
               # inside name[16] at 0x08 in this record, so writing one left the name without its
               # terminator and the strcmp failed — reported as the same number a bad version gets.
               # d2host now converts the save into the era's record (packages/d2engine/charrecord.zig)
               # and 1.06b takes the character. What stops it now is a call through a null pointer
               # (EIP=0) shortly after BITMANIP_Initialize @10126 — the same wall 1.07 hits. It is
               # NOT the callback table (every tail slot is a reporting stub now and none fired),
               # NOT the game-data vtable (filling past its four methods changed nothing), and NOT
               # BITMANIP_Initialize's own arity (the real one is `ret 0xc`, three stdcall args,
               # and ours is the same — 1.10f's is instruction-identical besides).
               #
               # The fault is very likely a JUMP through a null pointer rather than a call: the
               # stack at the fault holds a heap value where a call's return address would be. Fog
               # now logs BITMANIP_Initialize's engine-side caller for exactly this; on 1.06b those
               # are 0x6fceb7ee and 0x6fcbc85a, which is where to disassemble forward from.
               #
               # NOT the join translation either, which was the obvious suspect and is ruled out. Classic
               # takes 0x61 at 28 bytes — 1.06b's own C->S table says so — and 28 is reachable two
               # ways: a 10-byte preamble with a 16-byte name, or an 11-byte one with a 15-byte
               # name. cs_packets picks the first. Forcing the second makes the engine answer the
               # join with NOTHING AT ALL rather than with GameFlags, so the first is right and the
               # name does arrive where this build reads it.
